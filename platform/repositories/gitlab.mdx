## Choose an access level

Hacktron supports two GitLab access options. Choose the service account's role
based on who will manage webhooks and repository clone credentials.

<Tip>
  **Maintainer: automatic setup (recommended)**

GitLab requires Maintainer access to create project webhooks and read-only
clone credentials. With this role, Hacktron manages both automatically for
your selected projects.

</Tip>

<Info>
  **Developer: manual setup**

Developer access lets Hacktron read merge requests and post review comments.
A [read-only deploy token provides repository cloning access](#developer-access-setup),
and a GitLab Maintainer or Owner configures the webhook separately. This lets
the service account stay at Developer access while an authorized person
handles the setup operations that require a higher role.

</Info>

## Prerequisites

You need to be a Hacktron organization admin to connect GitLab and manage its settings.

A GitLab group Owner creates the service account. For the Developer option,
you also need someone with permission to create deploy tokens and webhooks:
a group Owner for group-level setup, or a project Maintainer or Owner for
project-level setup. The service account itself can keep Developer access.

## Configure access

<Steps>
  <Step title="Open Service Accounts page">
      In GitLab, under the group you want to connect to Hacktron, go to
      **Settings** and select **Service Accounts**.
    <img src="/images/gitlab_sa.png" alt="GitLab Service Accounts" />
  </Step>
  <Step title="Create a new service account">
    Give the service account a descriptive name, e.g. "Hacktron".

    <img src="/images/create_sa.png" alt="Create Service Account" />

    Click **Create**.

  </Step>
  <Step title="Choose the service account's access level">
    Grant access to the group or projects you want Hacktron to scan.

    <Tabs>
      <Tab title="Maintainer (recommended)">
        Grant **Maintainer** access. Hacktron creates project webhooks and
        repository clone credentials automatically.

        <img
          src="/images/invite_sa.png"
          alt="Grant the Hacktron service account Maintainer access in GitLab"
        />
      </Tab>
      <Tab title="Developer">
        Grant **Developer** access. After connecting, [save a read-only deploy
        token and configure webhooks manually](#developer-access-setup).

        Hacktron detects the account's access level automatically.
      </Tab>
    </Tabs>

  </Step>
  <Step title="Create a new personal access token">
    In the service account page, select the service account and click on
    **Manage access tokens**.

    <img src="/images/manage_token.png" alt="Manage Service Account Tokens" />

    Click **Add new token** and enable `api`, `read_api`, and `read_user`,
    as listed in Hacktron's setup instructions. Set an expiration date and
    click **Generate token**.

    <Info>
      **Why these token scopes?**

      - `api`: Post review comments and, with Maintainer access, manage webhooks
        and clone credentials.
      - `read_api`: Read project and merge request information, including diffs.
      - `read_user`: Identify the connected service account.
    </Info>

    <Warning>
      Rotate the personal access token before it expires to avoid service interruption.
    </Warning>

  </Step>
  <Step title="Connect GitLab">
    In Hacktron, go to **Integrations** and click **Connect** under **GitLab**.
    Paste the personal access token and click **Connect GitLab**.

    <img
      src="/images/gitlab-connect-access.png"
      alt="Hacktron GitLab connection panel explaining Maintainer and Developer access"
    />

  </Step>
  <Step title="Select projects">
    Go to **Repositories** and select the GitLab projects Hacktron can access.

    With Maintainer access, webhook setup is automatic. With Developer access,
    complete the setup below before starting scans.

  </Step>
</Steps>

Connecting GitLab does not turn on merge request reviews. Once access is ready,
[enable Code Review for the repositories and branches you want covered](/code-review/setup#configure-code-review).

## Developer access setup

Complete these steps when the service account has Developer access. Hacktron
shows **Needs setup** until a deploy token is saved.

<Steps>
  <Step title="Create a read-only deploy token in GitLab">
    Ask a GitLab group Owner or project Maintainer to open the group or project,
    then go to **Settings** → **Repository** → **Deploy tokens**. Select
    **Add token**, give it a name, enable only `read_repository`, and click
    **Create deploy token**.

    Copy both the username and token before leaving the page. GitLab only shows
    the token once.

    <Note>
      A group deploy token covers the projects in that group. The token saved
      in Hacktron must cover every selected private project. A project deploy
      token works when you are connecting only that project.
    </Note>

  </Step>
  <Step title="Save the deploy token in Hacktron">
    Open **Integrations** → **GitLab** → **Manage**. Under **Webhooks and deploy
    tokens**, enter **Deploy token username** and **Deploy token**, then click
    **Save**.

    <img
      src="/images/gitlab-developer-access.png"
      alt="Hacktron GitLab settings showing where to enter and save the deploy token username and token"
    />

  </Step>
  <Step title="Configure the webhook in GitLab">
    In the same Hacktron panel, copy the webhook **URL** and **Secret token**.

    In GitLab, open **Settings** → **Webhooks** on each selected project and
    click **Add new webhook**. Paste the full URL, including its query string,
    and the secret into GitLab's **Secret token** field.

    Enable these triggers:

    - **Push events**
    - **Merge request events**
    - **Comments**

    Keep **Enable SSL verification** selected and click **Add webhook**.

    <Tip>
      On GitLab Premium or Ultimate, a group Owner can create one
      [group webhook](https://docs.gitlab.com/user/project/integrations/webhooks/#group-webhooks)
      instead of a webhook on each project. Configure it at either the group
      or project level to avoid duplicate deliveries.
    </Tip>

  </Step>
  <Step title="Enable merge request reviews">
    [Enable Code Review](/code-review/setup#configure-code-review) for the selected
    repositories. Open or update a merge request to trigger a review.
  </Step>
</Steps>

<Note>
  Saving a deploy token clears **Needs setup**, but does not verify that you
  created the webhook. If reviews do not run, check the webhook URL, secret, and
  triggers in GitLab. If repository access fails, check the deploy token's
  scope, expiration, and project coverage.
</Note>

## Self-hosted GitLab / GitLab Enterprise

Both Maintainer and Developer setup work with self-hosted GitLab and GitLab
Enterprise. Follow the steps above using your own instance.

<Note>
  On self-managed GitLab, service accounts require GitLab EE, and by default
  only an instance administrator can create them (administrators can also allow
  top-level group Owners to create them). Alternatively, a personal access token
  from an existing user with the chosen access level and the same scopes can
  also be used.
</Note>

When you open the **Connect GitLab** modal in Hacktron, select **Self-hosted /
GitLab Enterprise** and enter your instance's base URL (e.g.
`https://gitlab.example.com`) before entering the token.

- Your GitLab instance must be reachable from Hacktron over HTTPS with a valid TLS certificate.
- GitLab installed under a URL subpath (e.g. `https://example.com/gitlab`) is not supported. Use the instance's base URL.
- For Developer access, use the webhook URL and secret shown in Hacktron for this connection.
